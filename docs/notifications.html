Notifications

Get a Telegram, Slack, webhook or email message when backups and restores finish or fail.

How it works#

A Notifier watches the Backups and Restores in its own namespace. When one reaches Completed or Failed and the event is in the Notifier's events, it sends one message. Each Notifier has exactly one channel. For several channels, create several Notifiers.

apiVersion: planb.sina-devel.github.io/v1alpha1
kind: Notifier
metadata:
  name: ops-telegram
  namespace: db
spec:
  events: [BackupFailed, RestoreFailed]       # default
  selector:                                   # optional: only matching Backups/Restores
    matchLabels: { planb.sina-devel.github.io/schedule: app-nightly }
  suspend: false
  telegram:
    chatID: "-1001234567890"
    botToken: { name: telegram-bot, key: token }

Events#

EventSent when
BackupCompleteda Backup reaches Completed
BackupFaileda Backup reaches Failed, including validation failures such as a read-only location
RestoreCompleteda Restore reaches Completed
RestoreFaileda Restore reaches Failed or FailedValidation

Only failures are sent by default. Add BackupCompleted if you want a message for every successful backup, for example as a heartbeat for a nightly schedule.

Channels#

Telegram#

telegram:
  chatID: "-1001234567890"           # user ID, group ID or @channelname; the bot must be a member
  botToken: { name: telegram-bot, key: token }
  apiURL: https://api.telegram.org   # default; a self-hosted Bot API server or reverse proxy

Create a bot with @BotFather, add it to the group or channel, and get the chat ID, for example from https://api.telegram.org/bot<token>/getUpdates after sending the bot a message.

Slack, Mattermost, Rocket.Chat#

slack:
  webhookURL: { name: slack-webhook, key: url }   # incoming webhook URL, kept in a Secret
  channel: "#backups"                             # optional, where the server allows overriding it

Webhook#

webhook:
  url: https://hooks.example.com/planb            # or urlSecret: { name: ..., key: ... }
  headers: { Authorization: "Bearer ..." }

planb POSTs one JSON object per event. A 2xx response counts as delivered:

{
  "event": "BackupCompleted",
  "cluster": "prod-eu",
  "kind": "Backup",
  "namespace": "db",
  "name": "app-nightly-20261029010000",
  "phase": "Completed",
  "message": "",
  "source": "postgres · postgres.db.svc / app",
  "schedule": "app-nightly",
  "storageLocation": "default",
  "sizeBytes": 8271,
  "items": 2,
  "startTime": "2026-10-29T01:00:01Z",
  "completionTime": "2026-10-29T01:00:09Z"
}

Restores also carry "backup", the Backup they restored from. Test messages have "event": "Test".

Email#

email:
  host: smtp.example.com
  port: 587                       # default
  tls: StartTLS                   # StartTLS (default, required upgrade) | TLS (implicit, port 465) | None
  from: planb@example.com
  to: [ops@example.com]
  credentials: { name: smtp-credentials }   # keys username/password; omit for no AUTH

Delivery#

  • At least once. After a successful delivery, the Notifier's name is added to the Backup's or Restore's planb.sina-devel.github.io/notified annotation. Failed deliveries are retried every minute for an hour.
  • Only new events. Backups and Restores created before the Notifier, and Backups imported by sync, are never notified.
  • Status. kubectl get notifiers shows the channel, the events, the phase (Ready or Failed) and when the last message was sent. A failure's reason is in status.message and in a Warning event.
  • Cluster name. Set manager.clusterName in the chart so messages say which cluster sent them.

Sending a test message#

Use Test in the UI, or change the planb.sina-devel.github.io/test annotation to any new value:

kubectl annotate notifier ops-telegram -n db planb.sina-devel.github.io/test="$(date +%s)" --overwrite
kubectl get notifier ops-telegram -n db      # PHASE Ready, LAST SENT just now
kubectl describe notifier ops-telegram -n db # the error, if it failed

Proxies#

If Telegram, Slack or your webhook is only reachable through a proxy, set it in the chart. The proxy would also apply to the Kubernetes API, so exclude the cluster:

manager:
  extraEnv:
    - { name: HTTPS_PROXY, value: "http://proxy.internal:3128" }
    - { name: NO_PROXY, value: "10.0.0.0/8,.svc,.cluster.local,localhost" }
