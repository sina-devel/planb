Retries and reliability

Networks drop, providers throttle and databases restart. planb retries transient failures at three levels, resumes interrupted transfers, and never repeats a step that could corrupt a restore.

Three layers of retries#

LayerWhat's retriedHow
1. S3 requestevery single HTTP request: throttling, 5xx, timeouts, connection errorsup to 10 tries, exponential backoff from 500 ms to 15 s with jitter
2. Operationeach object copy, listing, dump file, download and database connectionspec.job.retry: 5 attempts, 2 s doubling to at most 1 min, with jitter
3. Jobthe whole backup or restorespec.job.backoffLimit (default 1): Kubernetes starts a new Pod

Retries happen inside the Job, so a Backup stays InProgress while it retries. Each retry is logged with the error, the attempt number and the wait:

kubectl logs -n db job/planb-backup-app-1 | grep retrying
level=WARN msg="retrying after error" operation="copy s3://media/uploads/a.jpg" attempt=1 of=5 wait=1.4s error="...connection refused"

Configuring#

spec.job.retry is available on Backups, Schedule templates and Restores:

spec:
  job:
    retry:
      attempts: 8           # per operation, including the first try (1–50, default 5)
      initialBackoff: 2s    # wait before the second try, doubled after each failure (default 2s)
      maxBackoff: 2m        # cap on the wait (default 1m)
    backoffLimit: 2         # then restart the whole Job up to twice

Each wait is between half and all of the current backoff, picked at random. Parallel workers therefore spread out instead of retrying together, and a rate limit always gets real breathing room. The two layers multiply: each operation attempt already includes layer 1's request retries. With the defaults, an S3 operation survives outages of a few minutes. Raise attempts and maxBackoff for providers with long maintenance windows.

What's retried and what isn't#

Retried

Connection refused or reset, DNS failures, timeouts, unexpected EOF. S3 SlowDown, Throttling, RequestTimeout, InternalError, HTTP 408, 429 and 5xx, expired temporary tokens. PostgreSQL "connection refused", "the database system is starting up", "too many clients", "server closed the connection unexpectedly".

Fails at once

Wrong keys or password, access denied, missing bucket, key or database, TLS certificate errors, an object that changed during a resumed download, SQL errors in a restore, invalid arguments. Retrying these only delays the error message.

Resuming instead of restarting#

  • Downloads (bucket restores, the source side of bucket backups, PostgreSQL restores) resume at the byte where they stopped, using a range request. Every resume is tied to the object's ETag: if the object changed in the meantime, the download fails instead of joining two versions.
  • Listings continue after the last key they returned.
  • Uploads are multipart. Each 64 MiB part is retried by layer 1. If an upload fails for good, the incomplete multipart upload is aborted so it doesn't keep costing storage.

PostgreSQL: safe to repeat?#

Re-running a step must never leave a database worse off. planb decides per step:

StepRetried afterWhy
pg_dump, pg_dumpallany transient failureread-only on the server; the new upload replaces the partial one
create databaseany transient failurechecks whether the database exists before creating it
pg_restore with cleanany transient failure--clean drops what the failed attempt created
pg_restore without cleanonly failures to connecta half-restored database would make a second run fail on duplicates
psql (full-server and globals)only failures to connectSQL replay isn't idempotent

When a restore can't be retried, it fails with the original error. Re-run it with clean: true, or into a fresh database name.

Job-level settings#

spec.job fieldUse
backoffLimitNew Pods after the in-Job retries are used up (default 1). The Job's own backoff applies between Pods.
activeDeadlineSecondsHard limit for the whole Job, retries included. The Backup fails with DeadlineExceeded.
resourcesCPU and memory for the agent. About 64 MiB per concurrent upload plus the PostgreSQL tools.
nodeSelector, tolerationsWhere the Job runs, for example close to the database.
serviceAccountNameFor IAM roles (IRSA, Workload Identity) instead of access keys.
imageAnother agent image, for example with a different PostgreSQL client.
