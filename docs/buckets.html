S3 buckets

Snapshot every object in a bucket, or under a prefix, into the backup location, then copy it back, optionally pruning the target so it matches the snapshot exactly.

Backup#

apiVersion: planb.sina-devel.github.io/v1alpha1
kind: Backup
metadata:
  name: media-2026-10-29
  namespace: db
spec:
  storageLocation: default
  bucket:
    endpoint: s3.eu-central-1.amazonaws.com
    region: eu-central-1
    bucket: media
    prefix: uploads/              # optional: only objects under this prefix
    credentials: { name: media-bucket }

The source takes the same fields as a storage location, so it can be on a different provider, endpoint or account from the backup bucket. Objects are streamed straight from source to destination, four at a time, with the keys relative to prefix:

s3://media/uploads/2026/a.jpg  →  s3://my-backups/planb/backups/media-2026-10-29/bucket/2026/a.jpg

What's copied#

  • Every backup is a full copy. Backups aren't incremental and share nothing, so each one can be restored or deleted on its own. Storage grows with size × number of kept backups. Use keepLast and TTLs to bound it, or a provider-side lifecycle rule to move old backups to cheaper storage.
  • Object data and Content-Type are kept. User metadata, tags, ACLs, storage classes and older object versions are not.
  • Folder marker objects (zero-byte keys ending in /) are skipped.
  • If the source is the storage location's own bucket, planb's backups/ folder is left out, so backups never contain earlier backups.
  • The copy isn't an atomic snapshot: objects changed while the backup runs may or may not be included. For a point-in-time view, enable bucket versioning or pause writers.

Restore#

apiVersion: planb.sina-devel.github.io/v1alpha1
kind: Restore
metadata:
  name: media-restore
  namespace: db
spec:
  backupName: media-2026-10-29
  bucket:
    target:                       # default: the original bucket and prefix
      endpoint: s3.eu-central-1.amazonaws.com
      region: eu-central-1
      bucket: media-restored
      prefix: ""
      credentials: { name: media-bucket }
    overwrite: true               # default
    prune: false                  # default

A restore copies every object of the backup into the target prefix, keeping relative keys. What it does with objects that are already there depends on two options:

overwritepruneResult in the target
truefalseObjects in the backup are written over existing ones. Other objects stay. (default)
falsefalseOnly missing objects are added; existing keys are never touched. Good for "fill in what's lost".
truetrueThe target prefix ends up exactly like the backup: every object restored, everything else under the prefix deleted.
falsetrueExisting keys are kept as they are, and objects that aren't in the backup are deleted.

Prune#

prune: true rolls a bucket back to the snapshot. After every object has been copied, planb lists the target prefix and deletes each object whose relative key isn't in the backup, 1,000 keys per request. If any copy fails, nothing is deleted. The count is in status.deletedItems and in the completion message:

kubectl get restore media-restore -n db -o jsonpath='{.status.message}'
restore completed: 6 items, 1048611 bytes, 1 extra objects deleted
Prune deletes data

It removes everything under the target prefix that isn't in the backup, including objects written after the backup was taken. With an empty target prefix, that's the whole bucket. Double-check target before applying, and restore into a fresh prefix first if you're unsure.

Two safety rules always apply: objects outside the target prefix are never touched, and when the target is the storage location's own bucket, planb's backups/ folder is protected. While pruning, the Job keeps the list of backed-up keys in memory, roughly 100 bytes per object, so give it more memory for buckets with millions of objects.

Large buckets#

  • Interrupted listings and downloads resume where they stopped, and each object copy is retried on its own; see Retries and reliability.
  • Objects of unknown size are uploaded in 64 MiB parts. Set PLANB_PART_SIZE_MB for objects above 640 GiB.
  • Set spec.job.activeDeadlineSeconds to bound how long a backup may run.
