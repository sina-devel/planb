Concepts

How planb is built: the resources you create, what the operator does with them, and how data gets to the bucket.

Resources#

planb adds five namespaced resources to the API group planb.sina-devel.github.io/v1alpha1. A resource only refers to Secrets and other planb resources in its own namespace.

KindShort namePurpose
BackupStorageLocationbslA bucket where backups are written. Checked periodically and synced back into the cluster.
BackupOne backup of a PostgreSQL server or of a bucket. Deleting it deletes its data.
ScheduleCreates Backups from a template on a cron schedule, and keeps the last N.
RestoreRestores a Backup to where it came from or to a different target.
NotifierSends a Telegram, Slack, webhook or email message when Backups or Restores finish.

Architecture#

planb is a single binary with three modes:

  • manager: the operator. It watches the resources, creates Jobs, records results, garbage-collects expired backups and sends notifications. It never touches your data itself.
  • agent: runs inside each backup or restore Job and moves the data.
  • ui: the optional web UI and its JSON API.
  1. You create a Backup, or a Schedule creates one.
  2. The operator checks it: the storage location must exist, be ReadWrite and be reachable. It then creates a Job named planb-backup-<name> in the Backup's namespace.
  3. The Job runs the same image in agent mode. The image contains the PostgreSQL client tools. The agent streams data from the source into the bucket.
  4. The agent reports size, item count and files through the container's termination message.
  5. The operator copies the result into the Backup's status, sets the expiration and writes planb-backup.json next to the data. Sync uses that file to recognise finished backups, so a folder without it is never imported.

Restores work the same way, with a Job named planb-restore-<name> running in the opposite direction.

Streaming, not staging#

Nothing is written to local disk. A PostgreSQL backup is pg_dump | upload and a restore is download | pg_restore. Uploads use S3 multipart upload in 64 MiB parts, so memory use stays flat however big the dump is. One object can be up to 10,000 parts, about 640 GiB by default. Set the PLANB_PART_SIZE_MB environment variable in the image to raise the part size and with it the limit.

Storage layout#

s3://<bucket>/<prefix>/backups/<backup-name>/
├── planb-backup.json          # the Backup object (spec + status): used by sync
├── postgres/
│   ├── app.dump               # pg_dump --format=custom, one per database
│   ├── globals.sql.gz         # roles and tablespaces (includeGlobals)
│   └── all.sql.gz             # pg_dumpall, when no databases are listed
└── bucket/
    └── ...                    # objects of a bucket backup, with relative keys

Each backup is a self-contained folder. You can copy, inspect or restore it by hand with standard tools; see manual restore.

Credentials and security#

  • Secrets reach the Jobs only through secretKeyRef environment variables. They never appear in a resource, in Job arguments or in logs.
  • When an S3 spec has no credentials, planb uses the standard AWS credential chain: the AWS_ACCESS_KEY_ID/AWS_SECRET_ACCESS_KEY environment variables, then the instance or pod IAM role. Use spec.job.serviceAccountName for IRSA or Workload Identity.
  • Jobs run as a non-root user with a read-only root filesystem, no privilege escalation, all capabilities dropped and the RuntimeDefault seccomp profile.
  • The operator's ClusterRole lets it get (not list) Secrets and namespaces, create and delete Jobs, read Pods to collect results, and record Events. With manager.watchNamespace it only watches one namespace.

Lifecycles#

ResourcePhases
BackupNew → InProgress → Completed or Failed; Deleting while its data is removed
RestoreNew → InProgress → Completed or Failed; FailedValidation when the spec doesn't fit the backup
BackupStorageLocationAvailable or Unavailable, checked every syncPeriod (default 1m)
ScheduleEnabled, Paused or FailedValidation (for example, a bad cron expression)
NotifierReady, or Failed after a failed delivery until the next success

Each step is recorded as a Kubernetes Event on the resource, visible in kubectl describe.

Compared with Velero#

planb borrows Velero's resource model: storage locations, backups, schedules, restores, TTLs and sync from storage. Velero backs up Kubernetes objects and volumes. planb backs up data services through their own tools: pg_dump for PostgreSQL and object copies for buckets. The two complement each other: use Velero for manifests and PVCs, and planb for consistent logical database dumps and bucket snapshots.
