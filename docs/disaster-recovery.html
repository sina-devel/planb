Disaster recovery

Restore into a new cluster after losing the old one, rehearse it regularly, and recover by hand if planb itself isn't available.

Restore in a new cluster#

Everything planb needs is in the bucket: the data and a planb-backup.json describing each backup. A new cluster only needs planb, the credentials and a storage location pointing at the same bucket and prefix.

  1. Install planb in the new cluster (Getting started).
  2. Create the namespace and Secrets: the S3 key for the backup bucket, and the database or bucket credentials for the restore targets.
  3. Attach the bucket read-only, with the same bucket and prefix as before: 
    apiVersion: planb.sina-devel.github.io/v1alpha1
kind: BackupStorageLocation
metadata:
  name: recovery
  namespace: db
spec:
  accessMode: ReadOnly        # restores only: nothing in the bucket can be changed or deleted
  syncPeriod: 30s
  s3:
    endpoint: s3.eu-central-1.amazonaws.com
    region: eu-central-1
    bucket: my-backups
    prefix: planb
    credentials: { name: backup-bucket }
  4. Wait for the backups to appear. Imported backups keep their original names and labels: 
    kubectl get backups -n db -l planb.sina-devel.github.io/storage-location=recovery
  5. Restore. If the database host is different in the new cluster, set postgres.target: 
    apiVersion: planb.sina-devel.github.io/v1alpha1
kind: Restore
metadata:
  name: app-recovery
  namespace: db
spec:
  backupName: app-nightly-20261029010000
  postgres:
    target:
      host: postgres.db.svc
      credentials: { name: postgres-credentials }
  6. Hand over ownership when the new cluster becomes the primary: change the location to ReadWrite, or create a new one, and recreate the Schedules.
Namespaces must match

Sync imports backups into the namespace of the storage location. Put the location in the namespace where you want the Backups, which doesn't have to be the original one.

Rehearse#

A backup you haven't restored is a hope, not a backup. A cheap, regular drill:

  • A Schedule takes nightly backups, with a Notifier for BackupFailed.
  • Once a week, a script or CI job creates a Restore of the newest backup with databaseMapping: {app: app_drill}, checks row counts or runs smoke queries, then drops app_drill.
  • Once a quarter, run the full new-cluster procedure above in a scratch cluster with a ReadOnly location.

The repository's hack/e2e-k8s.sh is an example of driving every feature with plain kubectl and checking the results.

Manual restore without planb#

The backup format is plain files, so you can always recover with standard tools:

# download a backup folder (any S3 tool works)
rclone copy s3remote:my-backups/planb/backups/app-nightly-20261029010000 ./backup

# per-database backup
createdb -h db.example.com -U postgres app
pg_restore -h db.example.com -U postgres --dbname=app ./backup/postgres/app.dump

# roles and tablespaces
gunzip -c ./backup/postgres/globals.sql.gz | psql -h db.example.com -U postgres -d postgres

# full-server backup, into an empty server
gunzip -c ./backup/postgres/all.sql.gz | psql -h db.example.com -U postgres -d postgres

# bucket backup: copy the objects back
rclone copy ./backup/bucket s3remote:media/uploads

planb-backup.json records the original spec, the time of the backup, the file list and the sizes.
