Schedules and retention

Create backups on a cron schedule, and control how long they're kept with keepLast, TTLs and deletion rules.

Schedules#

apiVersion: planb.sina-devel.github.io/v1alpha1
kind: Schedule
metadata:
  name: app-nightly
  namespace: db
spec:
  schedule: "CRON_TZ=Europe/Berlin 0 3 * * *"
  keepLast: 7
  skipIfRunning: true             # default
  paused: false
  template:                       # any Backup spec
    storageLocation: default
    ttl: 720h
    postgres:
      host: postgres.db.svc
      credentials: { name: postgres-credentials }
      databases: [app]

At each scheduled time the operator creates a Backup named <schedule>-<UTC time as YYYYMMDDHHMMSS>, for example app-nightly-20261029010000, labelled planb.sina-devel.github.io/schedule: app-nightly. The Backups are owned by nobody: deleting the Schedule leaves them, and their data, in place.

Cron syntax#

ExpressionRuns
0 3 * * *03:00 UTC every day
CRON_TZ=Europe/Berlin 0 3 * * *03:00 Berlin time, following daylight saving
*/15 * * * *every 15 minutes
0 2 * * 002:00 UTC on Sundays
@daily, @hourly, @weeklydescriptors
@every 6hevery six hours

An invalid expression puts the Schedule in FailedValidation with the parser error in status.message. status.nextScheduleTime shows when the next backup is due.

Behaviour#

  • skipIfRunning (default true): a run is skipped while the previous backup of this schedule is still New or InProgress. The skip is noted in status.message.
  • Missed runs: if the operator was down when one or more runs were due, it creates one backup for the most recent missed time as soon as it's back. Earlier missed runs are skipped.
  • Pause with paused: true, the UI's Pause button, or kubectl patch schedule app-nightly -n db --type=merge -p '{"spec":{"paused":true}}'.
  • Run now: the UI's Run now creates a Backup from the template straight away. With kubectl, create a Backup with the same spec.

Retention#

Three mechanisms decide when a backup goes away. They work together; whichever comes first wins.

keepLast#

Each time the schedule is reconciled, at least once per run, it deletes its oldest completed backups beyond keepLast, counted by creation time. Deleting them deletes their data. Failed and running backups don't count and aren't deleted. Backups are matched by the schedule label, so backups that sync imports from storage count too. 0 (the default) means "rely on the TTL only".

TTL#

Every Backup expires at completionTimestamp + ttl, shown in status.expiration and the EXPIRES column. Then the Backup and its data are deleted.

  • The default comes from the operator's --default-backup-ttl (chart: manager.defaultBackupTTL, default 720h = 30 days).
  • ttl: 0s keeps a backup forever, unless keepLast removes it.
  • Backups on ReadOnly locations are never garbage-collected.

Deleting a Backup#

Deleting a Backup deletes its data from the bucket: a finalizer removes the backup folder before the object goes away, and the phase reads Deleting meanwhile. The data is kept when:

  • the Backup has the annotation planb.sina-devel.github.io/retain-data: "true";
  • its namespace is being deleted, which protects against an accidental kubectl delete ns;
  • its storage location is ReadOnly, missing or being deleted;
  • the backup never started.
# keep the data, drop the object
kubectl annotate backup app-nightly-20261029010000 -n db planb.sina-devel.github.io/retain-data=true
kubectl delete backup app-nightly-20261029010000 -n db

Data kept this way is imported again by the next sync, unless the location's sync is off. To remove it later, delete the folder in the bucket, or let the re-imported Backup expire.

Example: daily, weekly and monthly#

Use one schedule per tier, each with its own TTL. A Notifier selector or a label on the template tells them apart.

spec: { schedule: "0 3 * * *",  keepLast: 7,  template: { ttl: 192h,  ... } }   # daily, a week
spec: { schedule: "0 4 * * 0",  keepLast: 5,  template: { ttl: 900h,  ... } }   # weekly, five weeks
spec: { schedule: "0 5 1 * *",  keepLast: 12, template: { ttl: 8800h, ... } }   # monthly, a year
